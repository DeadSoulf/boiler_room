# Обновление панели из GitHub

Начиная с v0.10.0 панель проверяет стабильные GitHub Releases репозитория
`DeadSoulf/boiler_room`. Установка начинается только после подтверждения
конкретной найденной версии. Автоматическая проверка не устанавливает прошивку.

## Как пользоваться

1. Подключите панель к Wi-Fi с доступом в интернет. Для проверки HTTPS нужны
   правильные дата и время; обычно они устанавливаются по NTP.
2. Откройте **Настройки → Сервис → Обновление** и нажмите **Проверить**.
   Проверка также выполняется автоматически после подключения и затем раз в 6 часов.
3. Если появилась новая совместимая версия, нажмите **Установить** и подтвердите
   показанный номер. Предложение обновить также появляется на главной странице.
4. Дождитесь загрузки, проверки, установки и перезагрузки. Страница показывает
   этап, объём данных и процент выполнения. Пока загрузка допускает отмену,
   доступна кнопка **Отменить**.
5. После перезапуска проверьте номер версии и итог обновления в том же разделе.

Эти же действия доступны во встроенном веб-интерфейсе. Для изменения состояния
требуется действующее сопряжение с кодом, показанным на физической панели.
После перезагрузки веб-страница восстанавливает опрос и проверяет версию устройства;
само восстановление связи ещё не означает успешную установку.

Во время установки запрещены конкурирующие команды изменения настроек.
Просмотр состояния остаётся доступным. Исчезновение интернета, недоступный GitHub
или отсутствие подходящего релиза не требуют форматирования накопителя.

## Flash, карта памяти и восстановление

Панель использует уже имеющуюся таблицу разделов 16 МБ: два раздела приложения
по `0x640000` байт, начиная с `0x10000` и `0x650000`. Образ загружается в
неактивный раздел. Текущая прошивка остаётся на месте до проверки нового файла
и выбора следующего загрузочного раздела. NVS настроек, разделы данных, ESP32-C6
и загрузчик при OTA не перепрошиваются.

microSD используется существующей службой журналирования для событий обновления.
Хранить ещё одну копию образа на карте не требуется; OTA работает без карты.
Уже вставленная карта не форматируется и её файлы не удаляются ради обновления.
Обычная ротация существующего журнала сохраняет прежние ограничения объёма.

Размер и SHA-256 файла должны совпасть с манифестом. Проверяются также проект,
плата, ESP32-P4 ES v1.3, Flash, таблица разделов, заголовок образа и точный
проверенный загрузчик с поддержкой отката. Перед выбором раздела выполняется
проверка образа средствами ESP-IDF.

Новая прошивка подтверждает запуск после устойчивой работы интерфейса и запуска
основных служб. Раннее автоматическое подтверждение Arduino отключено.
Сторожевой таймер первого запуска обеспечивает перезагрузку, если подтверждение
не состоялось в установленный срок. При следующем старте загрузчик возвращается
к предыдущему подтверждённому приложению. Проверка не зависит от доступности
интернета, подключённого MQTT-брокера или наличия внешних датчиков.

После успешного OTA предыдущая подтверждённая версия доступна для ручного
возврата, пока её раздел не используется следующей установкой. Возврат также
требует подтверждения показанного номера. До первого OTA резервного приложения
во втором разделе может не быть; тогда кнопка возврата недоступна. USB-резервная
копия на компьютере остаётся отдельным способом восстановления.

## Доверие к выпуску

Соединения с GitHub проверяют сертификаты через системный CA bundle. Допускаются
только HTTPS и предусмотренные хосты выдачи release assets; число перенаправлений,
размер ответов и время ожидания ограничены. Секретный GitHub-токен на панель
не записывается, приватные репозитории этот протокол не обслуживает.

Манифест `boiler-panel-ota.json` привязан к стабильному тегу, полному commit SHA,
имени бинарного файла, его длине и SHA-256. Этот механизм доверяет опубликованному
релизу через HTTPS. Это не цифровая подпись прошивки и не заявление о включённом
ESP secure boot. Администраторы репозитория остаются доверенными издателями.

Релизы без манифеста и подходящего образа не предлагаются для установки.
Версии сравниваются численно; черновики, prerelease, другой проект/плата,
несовпадающий номер, подозрительный URL и неверные хеши отклоняются.

## Подготовка следующего выпуска

После target-сборки `ci/verify_binary.py` и `ci/package_flash.py` создают:

- `BoilerPanel-vX.Y.Z-COM3.zip` — проверяемый пакет для USB;
- `BoilerPanel-vX.Y.Z-firmware.bin` — тот же образ для OTA;
- `boiler-panel-ota.json` — сведения о совместимости и точном исходном коммите.

`scripts/publish_github_release.py` принимает один из двух результатов:
`--hardware-result` после аппаратной установки либо `--ota-build-result` для
публикации проверенного OTA-кандидата перед его первой установкой. Второй режим
связывает успешную финальную сборку и браузерный отчёт с точными исходниками,
прошивкой, ZIP и манифестом; notes автоматически сообщают, что аппаратная
OTA-приёмка ожидается. Публичный stable/latest необходим панели для получения
кандидата, но сама публикация не подтверждает установку на устройство.

Оба режима сохраняют проверку версии, полного исходного commit, удалённого
тега и присутствия исходников в `origin/main`. Сначала создаётся черновик.
Все файлы и `SHA256SUMS.txt` загружаются и сверяются по размерам и SHA-256 GitHub;
только затем выпуск становится опубликованным и latest. Файлы существующего
выпуска с другим содержимым не перезаписываются.

После успешного OTA режим `--notes-only --hardware-result` обновляет только
notes при совпадении всего неизменяемого набора assets. Он не заменяет файлы
и не меняет `latest` или тег. Точный контракт proof и порядок аппаратной приёмки
описаны в [процессе выпуска](RELEASE_PROCESS_RU.md#публикация-ota-кандидата-перед-первой-аппаратной-установкой).

Порядок первоначальной установки и синхронизации описан в
[процессе выпуска](RELEASE_PROCESS_RU.md). Код OTA отсутствовал в v0.9.1, поэтому
первую версию с этой функцией нужно установить через проверенный USB-пакет.
