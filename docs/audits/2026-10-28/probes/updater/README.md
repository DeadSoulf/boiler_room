# Воспроизведение двух дефектов установщика

Проверки подготовлены для коммита `b700ef6f837f5fc1dbd0bad91a569159123c3851` проекта `DeadSoulf/boiler_room`. Они импортируют `apply_update.py` из указанного checkout и читают его `src/` и штатные fixtures `tests/fixtures/`. Запись исходного checkout не выполняется; байткод Python не сохраняется. Все изменения конфигурации, исходников fixtures и резервных копий выполняются внутри автоматически удаляемых `TemporaryDirectory`.

## Требования и запуск

Linux, Python 3.10 или новее и полный checkout с `apply_update.py`, `src/` и `tests/fixtures/`. Достаточно стандартной библиотеки Python; сеть, установка зависимостей, компилятор и подключённая плата не нужны.

Из корня checkout:

```bash
python3 -B docs/audits/2026-10-28/probes/updater/run.py
```

Параметр `--repo` задаёт **корень проверяемого репозитория**, а не каталог установленного BSP. Он поддерживается общим запуском и обеими отдельными проверками:

```bash
python3 -B docs/audits/2026-10-28/probes/updater/run.py --repo /path/to/boiler_room
python3 -B docs/audits/2026-10-28/probes/updater/config_validation_probe.py --repo /path/to/boiler_room
python3 -B docs/audits/2026-10-28/probes/updater/persistent_write_failure_probe.py --repo /path/to/boiler_room
```

Без `--repo` корень checkout ищется среди родительских каталогов файла проверки. Поэтому запуск не зависит от текущего рабочего каталога. Если пакет проверок находится отдельно от checkout, передайте `--repo` явно.

Каждый запуск выводит JSON в stdout. Скрипты не перезаписывают сохранённые доказательства. Сохранить новый результат можно обычным перенаправлением stdout после выбора имени файла. Поле `reference_commit` означает исходную проверенную версию; оно не утверждает, что текущий checkout имеет этот HEAD. Поле `updater_sha256` содержит фактический SHA-256 импортированного `apply_update.py`.

Общий `run.py` также принимает `--output DIR`: создаёт каталог при необходимости и записывает в него итоговый `results.json`, сохраняя тот же JSON в stdout. Файл `results.json` должен отсутствовать; существующий результат не перезаписывается. Эта опция относится только к общему runner:

```bash
python3 docs/audits/2026-10-28/probes/updater/run.py --repo . --output /tmp/boiler-audit-updater
```

## Значение кода завершения

| Код | Значение |
|---|---|
| `0` | **Ожидаемый дефект воспроизведён**; у `run.py` воспроизведены оба дефекта. Это не успешная проверка исправности установщика. |
| `1` | Проверка выполнилась, но ожидаемая совокупность признаков дефекта не получена. Нужно изучить JSON; этот код сам по себе не доказывает полноценное исправление. |
| `2` | Ошибка окружения/запуска либо непригодный контрольный baseline; воспроизведение нельзя оценить. |

После исправления production-кода эти проверки следует преобразовать в обычные регрессии с ожидаемым безопасным поведением. Существующие скрипты намеренно проверяют признаки исходных дефектов.

## Что проверяется

`config_validation_probe.py` создаёт четыре отдельные копии v0.3.1 fixture: контрольную и три с изменённым INI. Он проверяет, что preflight ошибочно принимает `board_build.chip_variant = esp32p4`, `board_build.mcu = esp32s3` и `lvgl@9.0.0`. Сборка и прошивка не выполняются. Доказано принятие несовместимой конфигурации, а не последствия выполнения полученной прошивки.

`persistent_write_failure_probe.py` после двух успешных замен исходников устанавливает мягкий `RLIMIT_FSIZE` в 512 байт. Затем он проверяет одновременно смешанное состояние исходников, целость резервных копий, обрезанный JSON-манифест и отказ штатного восстановления даже после снятия ограничения.

**Предупреждение о локальном ограничении процесса:** второй скрипт временно меняет только `RLIMIT_FSIZE` и обработчик `SIGXFSZ` своего процесса Python. Жёсткий лимит не меняется; прежние значения восстанавливаются в `finally` до попытки `restore()` и до вывода JSON. При запуске через `run.py` это отдельний дочерний процесс. Лимиты оболочки, родительского процесса и системы не меняются. Запускайте скрипт отдельным процессом указанными командами; не выполняйте его через `exec()` внутри собственного долгоживущего процесса Python. Исходный мягкий лимит должен превышать 512 байт; для обычного запуска подходит неограниченный лимит.

Это реальный локальный отказ записи `EFBIG`. Отключение питания и `ENOSPC` данным сценарием не моделируются. Положение ошибки разбора JSON может отличаться в зависимости от длины временного пути; критерием является невозможность разбора манифеста, а не точный номер колонки.

## Сохранённые доказательства

Исходные результаты аудита находятся в `../../evidence/updater/`:

- `config_validation_probe.json` — контрольный preflight и три неверно разрешённых переопределения.
- `persistent_write_failure_probe.json` — исходный результат отказа записи и восстановления.
- `portable_run.json` — результат запуска переносимой версии этих проверок на том же исходнике.
- `portability-check.json` — проверка запуска из другого каталога и перенесённого checkout с пробелами в пути, кодов завершения и отсутствия изменений исходников; также содержит SHA-256 файлов пакета проверок.

JSON содержит только относительные пути к проверяемым файлам, без абсолютных путей рабочей среды. Исходные JSON сохранены отдельно от результата новой обёртки, чтобы не смешивать первоначальное наблюдение и последующую проверку переносимости.
