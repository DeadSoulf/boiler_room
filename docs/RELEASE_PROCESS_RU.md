# Обязательный порядок обновления панели и GitHub

Правило пользователя от 04.11.2026: **не оставлять новую прошивку только на панели или в незавершённой ветке. Обновлять версии на GitHub без отдельного напоминания.**

Уточнение пользователя от 05.11.2026: **дальнейшие выпуски и установки выполнять через GitHub OTA**. Проверенный кандидат публикуется до установки и принимается по реальным результатам на панели. USB не подменяет этот путь при неудобстве или ошибке OTA. Первоначальная установка на устройство без OTA и восстановление через USB допустимы только по отдельному явному поручению пользователя.

## Когда пользователь просит установить обновление

1. Восстановить контекст по `docs/CHAT_HANDOFF_RU.md`, проверить реальную панель и свежий GitHub. Не собирать устаревшую `main` вместо установленной версии. Сохранить неизвестные локальные правки; не применять force push/reset к чужой работе.
2. Согласованную работу оформить новой версией. Обновить `src/panel_types.h`, корневой `VERSION`, README на обоих языках и `CHANGELOG.md`. Версия в вебе приходит из API, отдельную старую строку не оставлять.
3. Выполнить соответствующие изменениям тесты и target-сборку. Сохранить исходный commit, SHA-256 приложения и пакета. Ошибки общего legacy CI указывать отдельно, не маскировать отключением проверок.
4. **Подготовить GitHub OTA-кандидата:** включить исходный commit в `main`, создать тег `vX.Y.Z` на commit сборки, опубликовать проверенные `BoilerPanel-vX.Y.Z-COM3.zip`, `BoilerPanel-vX.Y.Z-firmware.bin`, `boiler-panel-ota.json` и `SHA256SUMS.txt`. Все файлы описывают один образ и исходный commit. Публиковать latest только после проверки всего набора assets по отдельному порядку ниже. До аппаратной приёмки notes сохраняют статус кандидата. ZIP остаётся частью проверяемого комплекта; его наличие не означает разрешение установить версию через USB.
5. Зафиксировать текущую версию и настройки панели по реальному API, сохранить имеющиеся резервные копии и журнал. Запустить штатную установку из GitHub OTA с подтверждением конкретной версии. OTA worker должен проверить плату/ревизию, Flash, разделы, загрузчик, манифест и образ и писать только неактивный слот приложения. Не стирать пользовательские настройки, C6, microSD или чужие разделы. Для обычного OTA не переводить панель в ROM и не делать обязательным новое USB-резервирование или внешнее чтение Flash.
6. Выполнить сетевую приёмку по критериям следующего раздела: проверить новую версию и identity, подтверждение запуска, `/health`, `/`, `/api/status`, службы, настройки и возможность возврата. Одного восстановления HTTP после перезагрузки недостаточно. Сетевая приёмка не означает независимое внешнее чтение Flash, визуальную проверку физического дисплея или испытание датчиков.
7. Добавить отчёт фактической OTA-приёмки, обновить `docs/verification/installed.json`, `docs/CHAT_HANDOFF_RU.md` и статус версии. Честно разделить внутреннюю проверку образа, наблюдения через сеть, нативные/браузерные тесты и отдельные аппаратные испытания. Обновить notes выпуска только способом, чей контракт подтверждён этим отчётом. Закрыть только те PR, чьи изменения действительно вошли в `main`; не объединять посторонние экспериментальные ветки.
8. Повторно прочитать GitHub и статус устройства. Финальный ответ должен ясно говорить, какая версия установлена, где её исходники/релиз, что проверено и что осталось. **Запись одной памятки при старом коде `main` не считается синхронизацией версии.**

Запрос пользователя на установку включает эту синхронизацию соответствующей версии. Новый функционал, смена Wi-Fi/MQTT, форматирование или управление оборудованием без запроса не выполняются.

## Сетевая приёмка OTA и границы доказательств

Для подтверждения сетевой установки сохранить до- и после-обновления реальные ответы панели, время наблюдений и привязку к точному GitHub Release. Применяются все следующие критерии:

1. Устанавливалась подтверждённая версия из своего GitHub Release. Тег, полный source commit, длина и SHA-256 прошивки совпадают с проверенным пакетом и манифестом. OTA worker проверяет полученные байты, записанный образ средствами ESP-IDF и ожидаемые версию, слот и хеш при первом запуске. Эти внутренние проверки не заменяют фиксацию источника и хешей выпуска в отчёте.
2. После перезапуска реальный `/api/status` сообщает ожидаемую новую `version`, `update.supported: true`, `update.busy: false`, `update.boot_pending: false` и завершение без ошибки. Зафиксировать `phase: "success"`, если оно наблюдалось. Автоматическая проверка GitHub позднее может заменить его на `"current"`; сама по себе фаза `current` установку не доказывает.
3. Проверить `update.automatic_rollback: true`, `update.rollback_available: true` и `update.previous_version`, совпадающую с версией перед установкой. В текущем backend первый флаг выставляется только при реально прочитанном состоянии текущего приложения `VALID` и допустимом выборе загрузки; второй требует подтверждённой записи обновления и проверенного предыдущего образа. Это свидетельства из кода/статуса панели, а не независимое чтение сырых otadata. Поздний `current` допустим вместе с новой версией, `error_code: 0` и указанными признаками завершённого OTA. Название `automatic_rollback` обозначает возможность отката, а не факт случившегося отката.
4. `/health`, `/` и `/api/status` должны отвечать после подтверждения запуска. Проверить соответствие полученной веб-страницы ожидаемому исходнику, Wi-Fi, готовность тача, ожидаемые службы/состояние microSD и сохранность пользовательских настроек. Отсутствие необязательного оборудования не подменять успешным испытанием этого оборудования; готовность драйвера тача не выдавать за физическое нажатие.

В сетевом отчёте явно указывать метод, например `verification_method: "github_ota_worker_and_http"`, и `independent_external_flash_readback: false`, если полного внешнего считывания не было. Успех SHA/ESP-IDF-проверок и boot self-check подтверждается штатным путём OTA и последующими статусами. Не приписывать API отсутствующие поля source commit, номера слота или сырых метаданных: объяснять, какие свойства проверены worker и какие наблюдались непосредственно через HTTP.

Для совместимости с действующим издателем `readback_and_metadata_verified: true` допустимо при подтверждённой **внутренней** проверке образа из Flash средствами `esp_ota_end`/`esp_image_verify` и `esp_partition_get_sha256`, повторной сверке хеша/identity после загрузки и подтверждённых `VALID`/записи `Confirmed`. Одной новой версии или восстановления HTTP для этого недостаточно. В таком отчёте обязательны явное описание внутреннего метода в `readback_method`, `device_internal_flash_validation_verified: true` и `independent_external_flash_readback: false`, если внешнего чтения не было. Проверка приложения средствами ESP-IDF не является независимым внешним SHA-256 полного BIN или всего раздела и не означает USB-readback. Если необходимая цепочка проверок не подтверждена, не ставить флаг ради финализации notes и не обходить отказ через USB.

Проверка доступности возврата не является выполненным испытанием отката или отключения питания. Эти испытания и физический осмотр дисплея отмечать выполненными только при реальном наблюдении. При неясном результате установки сохранить журнал и текущую рабочую версию; не заменять штатное OTA незапрошенной USB-прошивкой.

## Публикация OTA-кандидата перед первой аппаратной установкой

Панели нужен публичный stable/latest, чтобы получить образ по HTTPS; draft и prerelease она игнорирует. Поэтому издатель принимает **ровно один** из двух результатов:

- `--hardware-result FILE` — прежний режим после аппаратной установки: точные версия, исходный commit, SHA-256 прошивки, `readback_and_metadata_verified: true` и `http_ok: true`.
- `--ota-build-result FILE` — проверенная сборка для последующей OTA-приёмки. Автоматический заголовок notes явно сообщает, что аппаратная установка ещё не подтверждена. В `--notes` передают описание изменений; статус приёмки формирует издатель.

JSON `--ota-build-result` имеет следующий строгий контракт. Это **шаблон**, не результат проверки: значения в угловых скобках и размеры `0` заменяются фактическими данными; результат создают только после успешной финальной сборки и браузерного теста.

```json
{
  "schema": 1,
  "kind": "ota-build-candidate",
  "project": "DeadSoulf/boiler_room",
  "version": "v0.10.1",
  "source_commit": "<40 lowercase hex of build source>",
  "hardware_acceptance": "pending",
  "assets": {
    "BoilerPanel-v0.10.1-COM3.zip": {"size": 0, "sha256": "<SHA-256 of exact ZIP bytes>"},
    "BoilerPanel-v0.10.1-firmware.bin": {"size": 0, "sha256": "<SHA-256 of exact firmware bytes>"},
    "boiler-panel-ota.json": {"size": 0, "sha256": "<SHA-256 of exact manifest bytes>"}
  },
  "checks": {
    "final_build": {
      "source_commit": "<same build source commit>",
      "firmware_sha256": "<same firmware SHA-256>",
      "target": "jc4880p4",
      "exit_code": 0,
      "log": {"path": "artifacts/final-build.log", "sha256": "<SHA-256 of final build log>"}
    },
    "browser_tests": {
      "source_commit": "<same build source commit>",
      "test_script": "tests/equipment_web_browser.py",
      "report": {"path": "artifacts/equipment-web-review/browser-result.json", "sha256": "<SHA-256 of actual browser report>"}
    }
  }
}
```

Издатель читает указанные evidence-файлы внутри `artifacts/` и сверяет их SHA-256. В финальном build log необходим `[SUCCESS]` и недопустим `[FAILED]`. Браузерный отчёт должен содержать `result: "PASS"`, ширины `[320, 390, 768, 1280]`, реальные опросы HTTP, непустое описание покрытия, пустые `page_errors`/`mutation_requests` и `physical_panel_contacted: false`. Его хеши фактически загруженного `src/panel_web_page.h` и исполнявшегося теста должны совпадать с рабочими файлами и `git show <source>:<path>`. Результаты `REPRODUCED`/`FAIL` не подходят.

Тег обязан указывать на commit сборки, этот commit — входить в `origin/main`; удалённый тег проверяется отдельно. Исходники `src/`, сборочные файлы `ci/`, `VERSION` и браузерный тест должны соответствовать commit сборки без незакоммиченных добавлений. Сам издатель и документы могут находиться в более позднем commit: `HEAD == source` не требуется. Все три файла привязываются по длине и SHA-256; четвёртый asset `SHA256SUMS.txt` вычисляется из тех же байтов. Proof и локальные журналы не загружаются в Release.

Сначала выполните команду без `--publish` для локальной проверки; для публикации добавьте этот флаг:

```bash
python3 scripts/publish_github_release.py --source <build-commit> \
  --package artifacts/BoilerPanel-v0.10.1-COM3.zip \
  --ota-build-result artifacts/ota-build-result.json --notes release-notes.md --publish
```

Публикация создаёт draft, проверяет загрузку всех четырёх assets и только затем делает выпуск stable/latest. Повторный запуск с теми же файлами не заменяет assets и не переводит уже принятую аппаратно версию обратно в кандидаты. Факт установки и `installed.json` до проверки устройства не обновляют.

Для предусмотренного издателем режима аппаратной финализации `--hardware-result` после OTA дополнительно содержит `zip_sha256`, `ota_manifest_sha256` и `network_ota_install_verified: true`. Поле `readback_and_metadata_verified` заполняется по фактически подтверждённому методу: для внутренней проверки OTA обязательны `readback_method`, `device_internal_flash_validation_verified` и честное `independent_external_flash_readback`, как описано выше. Этот режим не превращает внутреннюю Flash-проверку и сетевой отчёт в результат внешнего readback. Проверяются **ожидаемые новые** слот и состояние OTA; неизменность otadata при OTA заявлять нельзя. Сохранность пользовательских настроек проверяют отдельно от допустимой записи служебного namespace `bp-update`.

```bash
python3 scripts/publish_github_release.py --source <same-build-commit> \
  --package artifacts/BoilerPanel-v0.10.1-COM3.zip \
  --hardware-result hardware-result.json --notes accepted-notes.md --notes-only --publish
```

`--notes-only` требует существующий публичный stable Release и точного совпадения имён, размеров и GitHub SHA-256 всех четырёх assets. Этот режим изменяет только `body`: он не создаёт Release, не дозагружает файлы, не меняет тег, `latest`, `draft` или `prerelease`. Если приёмка не пройдена, сохраняется честный статус кандидата; подставлять успешный аппаратный результат нельзя.

## Если этап не удался

Не обходить проверки. Сохранить резервную копию и журнал, сообщить точную проблему. Не отмечать версию установленной или Release завершённым без подтверждения. Если публикация недоступна, явно назвать, что осталось локально и чего нет на GitHub. Не обещать фоновое завершение.

Сбой OTA не разрешает автоматически подключаться к ROM-загрузчику или прошивать через USB. Если понадобится первоначальная установка или восстановление этим способом, требуется отдельное явное поручение пользователя. В таком отдельном процессе сохраняются проверки платы/разметки, резервирование и полное внешнее чтение записанного образа, предусмотренные USB-установщиком.

Резервные копии Flash, Wi-Fi/MQTT-пароли, PIN сопряжения и токены сессий **никогда не включать в публичный релиз, коммиты, отчёты или CI-артефакты**. Пакет релиза содержит только собранную программу, сравниваемые загрузочные файлы, инструкции и контрольные суммы; не считанные данные пользователя.
